## API Errors

<ExpandableGroup>
  <Expandable title="401 Unauthorized" default-open="false">
    **Cause:** Missing, expired, or invalid JWT token.

    **Solution:**
    - Ensure the `Authorization` header includes `Bearer ` (with a space) before the token
    - Check that the token has not expired (decode it at jwt.io to check the `exp` claim)
    - Verify the `JWT_SECRET` on the server matches the one used to sign the token
    - Generate a new token if the current one has expired
  </Expandable>

  <Expandable title="400 Bad Request — Subdomain is already taken" default-open="false">
    **Cause:** Another pod already uses this subdomain.

    **Solution:** Choose a different subdomain. Subdomains must be globally unique across all managed pods.
  </Expandable>

  <Expandable title="413 Payload Too Large" default-open="false">
    **Cause:** Upload would exceed the storage quota for the current tier.

    **Solution:**
    - Check current usage: `GET /api/v1/pods/:id/storage`
    - Delete unused content or media to free space
    - Upgrade to a higher tier for more storage
  </Expandable>

  <Expandable title="429 Too Many Requests" default-open="false">
    **Cause:** Rate limit exceeded.

    **Solution:**
    - Check the `X-RateLimit-Reset` response header for when the limit resets
    - Reduce request frequency
    - For bulk operations, use batch endpoints where available
  </Expandable>

  <Expandable title="404 Not Found — Pod not found" default-open="false">
    **Cause:** The pod ID does not exist or belongs to another user.

    **Solution:**
    - Verify the pod ID is correct
    - Ensure you are authenticated as the pod's owner
    - Pods marked as deleted return 404 — they cannot be recovered
  </Expandable>
</ExpandableGroup>

## Upload Token & Service API Errors

These errors come from the [Pod Files API and the Service API](/guides/local-publishing) used for pods of local (mobile-only) accounts.

<ExpandableGroup>
  <Expandable title="401 Invalid or expired upload token" default-open="false">
    **Cause:** The `rb_pod_…` token is unknown, expired (30 days by default), revoked, or belongs to a different pod.

    **Solution:**
    - Check that the `{podId}` in the URL is the pod the token was issued for
    - Request a new upload token through the Context Directory — tokens are revoked when a new one is issued with `revokeOthers`, when the key is rotated on a new device, and when the pod is suspended
  </Expandable>

  <Expandable title="403 Pod is suspended" default-open="false">
    **Cause:** The account's deletion is scheduled, so the pod was suspended and all uploads are refused.

    **Solution:** Cancel the account deletion. The pod becomes active again; request a new upload token afterwards — the old ones stay revoked.
  </Expandable>

  <Expandable title="403 Reserved path" default-open="false">
    **Cause:** A path segment starts with a dot (e.g. `.well-known/…` or `.htaccess`). Dot-paths are reserved for the platform.

    **Solution:** Upload content under `content/{type}/{slug}/…` or `media/…`. The `.well-known/roadbeat-publisher.json` document is written by the Context Directory, never by the app.
  </Expandable>

  <Expandable title="400 Invalid file path" default-open="false">
    **Cause:** The path contains characters other than `A–Z a–z 0–9 . _ - /`, is longer than 300 characters, or has `..`, `.` or empty segments (e.g. `content//news`).

    **Solution:** Use lowercase slugs with hyphens, e.g. `content/recipe/apple-pie/index.json`.
  </Expandable>

  <Expandable title="413 Item limit reached / Storage quota exceeded" default-open="false">
    **Cause:** The free tier for mobile accounts allows 200 content items and 500 MB. Each file is also limited to 25 MB.

    **Solution:**
    - Unpublish items you no longer need — deleting an item's `index.json` frees an item slot
    - Replacing an existing item does not count as a new item
    - Compress or resize media before upload
  </Expandable>

  <Expandable title="401 Service access is not configured" default-open="false">
    **Cause:** `POD_HOSTING_SERVICE_KEY` is not set on the Pod Hosting server, or it is shorter than 16 characters. The Service API fails closed.

    **Solution:** Set the same key (at least 16 characters) on Pod Hosting and on the Context Directory, then restart both services. A mismatch returns `401 Invalid service key`.
  </Expandable>
</ExpandableGroup>

## Content Generation Errors

<ExpandableGroup>
  <Expandable title="Page title or description shows [object Object]" default-open="false">
    **Cause:** Pods generated before the v1.2.1 release (2026-11-08) printed localized fields (`{ "en": "…", "de": "…" }`) and location objects as text, which produced `[object Object]` in titles, meta tags, page bodies and `manifest.json`.

    **Solution:** Update `@roadbeat/content-pod-generator` to a build that includes the v1.2.1 fix and republish the affected items. Custom templates should use the `localized` and `formatLocation` helpers — see [Localized Fields and Locations](/architecture/pod-structure#localized-fields-and-locations).
  </Expandable>

  <Expandable title="Template not found for content type" default-open="false">
    **Cause:** No Handlebars template registered for the content type.

    **Solution:** The `TemplateEngine` falls back to `base.hbs` for unknown types. If you need a custom template:

    ```typescript
    const engine = new TemplateEngine();
    engine.registerTemplate('my-content-type', myHandlebarsSource);
    ```

    Built-in templates: `news`, `event`, `recipe`, `job`, `profile`, `embed`.
  </Expandable>

  <Expandable title="Signature verification failed" default-open="false">
    **Cause:** Content was modified after signing, or the wrong public key is being used for verification.

    **Solution:**
    - Re-sign the content with the correct private key
    - Ensure `public_key.pem` on the pod matches the key used for signing
    - Check that the content was not modified after the `_signature` was computed
    - Use `ContentVerificationService.verifyPod()` to run a full integrity check
  </Expandable>

  <Expandable title="Checksum mismatch" default-open="false">
    **Cause:** A file's SHA-256 checksum does not match the value in `checksums.json`.

    **Solution:**
    - The file may have been corrupted during upload — re-upload it
    - Regenerate checksums: the `ChecksumService` can recompute all checksums
    - For migrations, run the verification step again — transient upload errors may cause mismatches
  </Expandable>
</ExpandableGroup>

## Storage Errors

<ExpandableGroup>
  <Expandable title="S3 access denied" default-open="false">
    **Cause:** Invalid or insufficient credentials for the S3 bucket.

    **Solution:**
    - Verify `accessKeyId` and `secretAccessKey` are correct
    - Check that the IAM policy allows `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`
    - Ensure the bucket exists and is in the correct region
  </Expandable>

  <Expandable title="SFTP connection failed" default-open="false">
    **Cause:** Cannot connect to the SFTP server.

    **Solution:**
    - Verify host, port, username, and key/password
    - Check that the SSH key file exists and has correct permissions (600)
    - Ensure the remote path exists and is writable
    - Test connectivity: `ssh -p 22 user@host`
  </Expandable>

  <Expandable title="CORS errors when accessing pod content" default-open="false">
    **Cause:** The storage provider does not include CORS headers.

    **Solution:**
    - For S3 buckets, configure CORS policy to allow `GET` from `*`
    - For SFTP/VPS hosting, add CORS headers in your web server config (Caddy/Nginx)
    - Managed pods handle CORS automatically
  </Expandable>
</ExpandableGroup>

## Reader Bundle & Own Storage Errors

These errors come from roadbeat Studio when it imports [reader bundles](/guides/reader-bundles) or publishes to [own storage](/guides/storage-providers#own-storage-for-studio-pods).

<ExpandableGroup>
  <Expandable title="413 POD_BUNDLE_TOO_LARGE" default-open="false">
    **Cause:** The package's listed bytes plus its manifest exceed the pod's free space within its tier. The response carries `neededBytes` and `freeBytes`.

    **Solution:**
    - Check the space up front: `GET /api/v1/integration/publishing/targets` → `pod.bundles.freeBytes`
    - Remove bundles or content that are no longer needed, or move the pod to a higher tier
  </Expandable>

  <Expandable title="409 BUNDLE_IMPORT_RUNNING" default-open="false">
    **Cause:** An import for the same item is still running.

    **Solution:** Wait for `pod.bundle.ready` or `pod.bundle.failed`, or poll `GET /api/v1/integration/pod/bundles/{bundleId}`, then retry. Imports interrupted by a restart are marked failed at start-up.
  </Expandable>

  <Expandable title="Bundle import refused — digest or signature" default-open="false">
    **Cause:** `package-manifest.json` does not hash to the `digest` you sent, the package is unsigned, or its Ed25519 signature does not verify against the reader's keys from the Schema Registry entry.

    **Solution:**
    - Send the SHA-256 of exactly the `package-manifest.json` that `sourceUrl` serves
    - Sign the package with a key listed in the reader's key document (`frame.bundle_signature_keys`) — Content Pods serve signed bundles only
  </Expandable>

  <Expandable title="Bundle import failed in the background" default-open="false">
    **Cause:** A file was larger than listed, its SHA-256 did not match, or the source could not be fetched (https only, no private addresses, same-origin redirects only).

    **Solution:** Check `error` (`code` and `message`) in `GET /api/v1/integration/pod/bundles/{bundleId}`. The live bundle stays untouched — fix the package or the source and import again. For local development, `WEBHOOK_ALLOW_PRIVATE_TARGETS=true` allows private and `http` sources.
  </Expandable>

  <Expandable title="Reader bundle does not show in the client frame" default-open="false">
    **Cause:** The bundle origin sends `X-Frame-Options`, lacks `Content-Security-Policy: frame-ancestors`, or the host does not match the client's `POD_BUNDLE_DOMAIN_PATTERNS`.

    **Solution:**
    - Serve bundles from a host of their own with `bundleResponseHeaders` (or the provisioned Caddy site) — never from the pod's own host
    - Default pattern: `*--b.pods.roadbeat.net`; in development set `EXTERNAL_READER_DEV_ORIGINS=http://localhost:3405`
    - Check the reader's registry entry has `frame.allow_pod_bundles: true`
  </Expandable>

  <Expandable title="POD_STORAGE_NOT_READY" default-open="false">
    **Cause:** An own storage target exists but has not passed its check (every change resets it to `unchecked`).

    **Solution:** Run `POST /api/v1/manage/content-pod/storage/{role}/check` (or **Check** in Settings → Content Pod → Storage) and fix what it reports. Publishing and bundle imports never fall back to the Studio's disk.
  </Expandable>

  <Expandable title="Storage check fails for the bundles target" default-open="false">
    **Cause:** The bundle origin needs a JavaScript MIME type for `.mjs`, `Content-Security-Policy: frame-ancestors`, `https`, and an origin of its own. A plain S3 bucket cannot send a CSP header.

    **Solution:** Put a CDN or web server (e.g. Caddy with the [bundle headers](/guides/reader-bundles#response-headers)) in front of the bucket, on a host different from the pod's pages and the content target. Missing CORS, `Accept-Ranges` or `nosniff` are only warnings.
  </Expandable>

  <Expandable title="POD_BUNDLE_TARGET_MISSING" default-open="false">
    **Cause:** The pod is on its own content storage but has no `bundles` target, so it has no bundle origin (`pod.bundles.supported = false`).

    **Solution:** Add and check a `bundles` storage target.
  </Expandable>

  <Expandable title="SFTP host key refused" default-open="false">
    **Cause:** The SFTP server's host key no longer matches the key pinned at the first passing check (`hostVerifier` returned `false`).

    **Solution:** Treat it as a possible man-in-the-middle first. The pin stays as long as host and port stay the same; only a new host or port drops it. If the server's key changed legitimately, remove the target and add it again, then re-run the check (a `bundles` target can only be removed while no bundles are served from it).
  </Expandable>
</ExpandableGroup>
