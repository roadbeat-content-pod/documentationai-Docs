title: Self-Hosting
description: Run the Content Pod stack locally or in production with Docker Compose.

The Content Pod ecosystem ships with a multi-stage Dockerfile and Docker Compose configuration for running the full stack — Pod Hosting API, Cloud Provisioner, Pod Dashboard, PostgreSQL, and Redis.

## Prerequisites

- **Docker** 24+ and **Docker Compose** v2
- Alternatively, for local development without Docker: **Node.js** 20+, **pnpm** 9+

## Quick Start with Docker Compose

<Steps>
  <Step title="Clone the repository">
    ```bash
    git clone https://github.com/roadbeat/content-pod.git
    cd content-pod
    ```
  </Step>
  <Step title="Start all services">
    ```bash
    docker compose up -d
    ```

    This starts 5 services:

    | Service | Port | Description |
    |---------|------|-------------|
    | `pod-hosting` | 3400 | Managed hosting REST API |
    | `pod-dashboard` | 3401 | Angular management dashboard |
    | `cloud-provisioner` | 3402 | Infrastructure provisioning API |
    | `postgres` | 5432 | PostgreSQL 16 database |
    | `redis` | 6379 | Redis 7 cache |
  </Step>
  <Step title="Verify health">
    ```bash
    curl http://localhost:3400/health
    curl http://localhost:3402/health
    ```

    Both endpoints should return `200 OK` with component health status.
  </Step>
</Steps>

## Building Individual Targets

The Dockerfile uses multi-stage builds. You can build each service independently:

<Tabs>
  <Tab title="Pod Hosting" icon="server">
    ```bash
    docker build -t pod-hosting --target pod-hosting .
    docker run -p 3400:3400 \
      -e DATABASE_URL=postgresql://postgres:postgres@host:5432/pod_hosting \
      -e REDIS_URL=redis://host:6379 \
      -e JWT_SECRET=your-secret-key \
      pod-hosting
    ```
  </Tab>
  <Tab title="Cloud Provisioner" icon="cloud">
    ```bash
    docker build -t cloud-provisioner --target cloud-provisioner .
    docker run -p 3402:3402 \
      -e DATABASE_URL=postgresql://postgres:postgres@host:5432/cloud_provisioner \
      -e HETZNER_API_TOKEN=your-token \
      cloud-provisioner
    ```
  </Tab>
</Tabs>

## Local Development (without Docker)

<Steps>
  <Step title="Install dependencies">
    ```bash
    pnpm install
    ```
  </Step>
  <Step title="Build all packages">
    ```bash
    pnpm -r run build
    ```
  </Step>
  <Step title="Create a .env file">
    The Pod Hosting app reads environment variables via NestJS `ConfigModule` from a `.env` in its working directory. Copy the template and adjust it:

    ```bash
    cp apps/pod-hosting/.env.example apps/pod-hosting/.env
    ```

    ```bash
    # apps/pod-hosting/.env
    DATABASE_URL="postgresql://postgres:YOUR_PASSWORD@localhost:5432/roadbeat_content_pod"
    JWT_SECRET=change-me
    PORT=3400

    # Service API for the Context Directory (pods for local accounts) — at least 16 characters,
    # must match the Context Directory's POD_HOSTING_SERVICE_KEY
    POD_HOSTING_SERVICE_KEY=change-me-at-least-16-chars
    # Where pod files are stored (dev: the static pod root served by serve-static-pod.ts)
    POD_FILES_ROOT=../../dev-pods/static
    # Public URL of a pod; {subdomain} is replaced
    POD_PUBLIC_URL_TEMPLATE=http://localhost:3403/{subdomain}
    ```

    With these defaults, files uploaded through the Pod Files API are served right away by the static pod server (`pnpm serve:static-pod`, port 3403), including `/.well-known/roadbeat-publisher.json`.

    <Callout kind="alert">
      The `roadbeat_content_pod` database must exist before starting the service. Create it with `CREATE DATABASE roadbeat_content_pod;` and run `pnpm --filter @roadbeat/pod-hosting exec prisma migrate deploy` to apply the schema.
    </Callout>
  </Step>
  <Step title="Run tests">
    ```bash
    pnpm -r test
    ```

    All tests should pass across all packages.
  </Step>
  <Step title="Start a service">
    ```bash
    # Pod Hosting (port 3400)
    cd apps/pod-hosting && pnpm start:dev

    # Cloud Provisioner (port 3402)
    cd apps/cloud-provisioner && pnpm start:dev
    ```
  </Step>
</Steps>

## Environment Variables

### Pod Hosting (`apps/pod-hosting`)

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `3400` | HTTP port |
| `DATABASE_URL` | — | PostgreSQL connection string |
| `REDIS_URL` | — | Redis connection string |
| `JWT_SECRET` | `dev-secret-change-in-production` | JWT signing secret |
| `NODE_ENV` | `development` | Environment (`development` / `production`) |
| `POD_HOSTING_SERVICE_KEY` | — | Shared key for the Service API (`/api/v1/service/*`), at least 16 characters; must match the Context Directory's value. Unset → the Service API rejects every request (fails closed) |
| `POD_FILES_ROOT` | `../../dev-pods/static` (relative to the working directory) | Directory with one folder per pod for files uploaded via the Pod Files API |
| `POD_PUBLIC_URL_TEMPLATE` | `https://{subdomain}.pods.roadbeat.net` | Public base URL of a pod; `{subdomain}` is replaced. Used for upload responses and the `.well-known` document's `podHost` |

<Callout kind="alert">
  If you serve pods from `POD_FILES_ROOT` with your own web server, make sure it serves **dotfiles** — Discovery Nodes fetch `/.well-known/roadbeat-publisher.json` to verify publishers, also while a pod is suspended. Uploads cannot create dot-paths, so only platform-written dotfiles exist.
</Callout>

### Cloud Provisioner (`apps/cloud-provisioner`)

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `3402` | HTTP port |
| `DATABASE_URL` | — | PostgreSQL connection string |
| `HETZNER_API_TOKEN` | — | Hetzner Cloud API token |
| `HETZNER_DEFAULT_LOCATION` | `fsn1` | Default server location |
| `HETZNER_DEFAULT_SERVER_TYPE` | `cx22` | Default server type |
| `CONTABO_CLIENT_ID` | — | Contabo OAuth client ID |
| `CONTABO_CLIENT_SECRET` | — | Contabo OAuth client secret |
| `CONTABO_API_USER` | — | Contabo API username |
| `CONTABO_API_PASSWORD` | — | Contabo API password |
| `CONTABO_DEFAULT_REGION` | `EU` | Default Contabo region |

<Callout kind="danger">
  Never use the default `JWT_SECRET` in production. Generate a strong random secret of at least 32 characters.
</Callout>

## Production Deployment

For production, the Docker images include:

- **Health checks** — `/health` endpoint polled every 30 seconds
- **Automatic restart** — `unless-stopped` restart policy
- **Security middleware** — rate limiting, security headers, input sanitization
- **Structured logging** — JSON-formatted logs for aggregation

### Recommended Production Setup

```yaml
# docker-compose.prod.yml additions
services:
  pod-hosting:
    environment:
      NODE_ENV: production
      JWT_SECRET: ${JWT_SECRET}       # From .env or secrets manager
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '1.0'
```
