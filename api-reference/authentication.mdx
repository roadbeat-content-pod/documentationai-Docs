title: Authentication

All Content Pod API endpoints require authentication via **JWT Bearer tokens** unless explicitly marked as public. Both the Pod Hosting API and Cloud Provisioner API use the same authentication scheme. Two exceptions in the Pod Hosting API: the [Service API](#service-key) uses `X-Service-Key`, and the [Pod Files API](#upload-tokens) uses scoped upload tokens.

## Authentication Header

Include a valid JWT token in the `Authorization` header of every request:

```bash
curl https://pods.roadbeat.net/api/v1/pods \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

<ParamField header="Authorization" param-type="string" required="true">
  `Bearer YOUR_JWT_TOKEN` — a valid, non-expired JWT token.
</ParamField>

## Token Format

JWT tokens are signed with HS256 and contain the following claims:

```json
{
  "sub": "user_abc123",
  "userId": "user_abc123",
  "email": "alice@example.com",
  "iat": 1709395200,
  "exp": 1709481600
}
```

<ResponseField name="sub" field-type="string" required="true">
  Subject — the user's unique identifier.
</ResponseField>

<ResponseField name="userId" field-type="string" required="true">
  User ID used for authorization checks (pod ownership, etc.).
</ResponseField>

<ResponseField name="email" field-type="string">
  User's email address.
</ResponseField>

<ResponseField name="iat" field-type="integer" required="true">
  Issued-at timestamp (Unix epoch seconds).
</ResponseField>

<ResponseField name="exp" field-type="integer" required="true">
  Expiration timestamp (Unix epoch seconds). Default token lifetime is 24 hours.
</ResponseField>

## Token Lifecycle

```mermaid
sequenceDiagram
    participant C as Client
    participant A as Auth Service
    participant P as Pod Hosting API

    C->>A: POST /auth/login (email + password)
    A-->>C: JWT token (24h expiry)
    C->>P: GET /api/v1/pods (Bearer token)
    P-->>C: 200 OK — pod list
    Note over C,P: Token expires after 24 hours
    C->>P: GET /api/v1/pods (expired token)
    P-->>C: 401 Unauthorized
    C->>A: POST /auth/refresh
    A-->>C: New JWT token
```

## Service Key

The **Service API** (`/api/v1/service/*`) is for platform services that manage pods on a user's behalf — today the Context Directory, which provisions pods for local (mobile-only) accounts. It does not accept user JWTs; every request carries the shared service key:

```bash
curl https://pods.roadbeat.net/api/v1/service/pods/$POD_ID \
  -H "X-Service-Key: $POD_HOSTING_SERVICE_KEY"
```

<ParamField header="X-Service-Key" param-type="string" required="true">
  The value of `POD_HOSTING_SERVICE_KEY` on the Pod Hosting server (at least 16 characters). The Context Directory must be configured with the same value.
</ParamField>

- The key is compared in constant time.
- The guard **fails closed**: if `POD_HOSTING_SERVICE_KEY` is not set or shorter than 16 characters, every request returns `401 Service access is not configured`.
- A wrong key returns `401 Invalid service key`.
- The service key only reaches pods that were created through the Service API (`provisionedBy: context-directory`).

## Upload Tokens

The **Pod Files API** (`/api/v1/pod-files/{podId}/…`) is authenticated with a **scoped upload token** instead of a JWT. The mobile app receives it via the Context Directory and uploads content directly into its own pod.

```bash
curl -X PUT https://pods.roadbeat.net/api/v1/pod-files/$POD_ID/content/news/hello/index.json \
  -H "Authorization: Bearer rb_pod_Jx3k9…" \
  -H "Content-Type: application/json" \
  --data-binary @index.json
```

<ParamField header="Authorization" param-type="string" required="true">
  `Bearer rb_pod_…` — an upload token issued by `POST /api/v1/service/pods/{id}/upload-token`.
</ParamField>

| Property | Value |
|----------|-------|
| Format | `rb_pod_` + 32 random bytes (base64url) |
| Scope | One pod — a token of another pod returns `401` |
| Lifetime | 30 days by default, at most 90 days |
| Storage | Only the SHA-256 hash is stored; the token is shown once |
| Revocation | `revokeOthers: true` on a new token, suspending the pod, or deleting the pod |

| Response | Meaning |
|----------|---------|
| `401 Missing upload token` | No `Bearer` header, or the token does not start with `rb_pod_` |
| `401 Invalid or expired upload token` | Unknown, expired, or revoked token, or a token of another pod |
| `403 Pod is suspended` | The token is valid but the pod is not active |

<Callout kind="info">
  The Pod Files API sends `Access-Control-Allow-Origin: *`. Because the token travels in a header and no cookies are used, this is safe — the endpoint behaves like a presigned upload URL.
</Callout>

## Public Endpoints

The following endpoints do **not** require authentication:

| Endpoint | Description |
|----------|-------------|
| `GET /health` | Health check |
| `GET /health/liveness` | Liveness probe |

All other endpoints return `401 Unauthorized` if the credential (JWT, service key, or upload token) is missing, malformed, or expired.

## Error Responses

### Missing Token

```json
{
  "statusCode": 401,
  "message": "Unauthorized"
}
```

### Expired Token

```json
{
  "statusCode": 401,
  "message": "Token has expired"
}
```

### Invalid Token

```json
{
  "statusCode": 401,
  "message": "Invalid token"
}
```

## Common Mistakes

<Expandable title="Why am I getting a 401?" default-open="false">
  Verify that:

  - The token is valid and not expired (check the `exp` claim)
  - The `Authorization` header includes the `Bearer` prefix and a space before the token
  - The token was issued for the correct API (Pod Hosting vs. Cloud Provisioner use the same JWT secret in a shared deployment)
  - The JWT secret on the server matches the one used to sign the token
</Expandable>

<Expandable title="How do I get a token for development?" default-open="false">
  In development, you can generate a token using the JWT secret from the environment:

  ```typescript
  import * as jwt from 'jsonwebtoken';

  const token = jwt.sign(
    { sub: 'dev-user', userId: 'dev-user', email: 'dev@example.com' },
    process.env.JWT_SECRET || 'dev-secret-change-in-production',
    { expiresIn: '24h' },
  );

  console.log(token);
  ```

  Or use the `jwt.io` debugger with the secret from your `.env` file.
</Expandable>

<Expandable title="Can I use API keys instead of JWT?" default-open="false">
  User-facing endpoints accept only JWT Bearer tokens. For machine-to-machine access between roadbeat platform services there is the [service key](#service-key); for uploads from the mobile app there are [scoped upload tokens](#upload-tokens). General-purpose API keys for third-party integrations are not available.
</Expandable>

## Security Best Practices

<Callout kind="tip">
  - Store tokens securely — never in local storage for web apps; prefer httpOnly cookies
  - Rotate the `JWT_SECRET` periodically in production
  - Use short-lived tokens (default 24h) and refresh as needed
  - Always use HTTPS in production to prevent token interception
</Callout>
